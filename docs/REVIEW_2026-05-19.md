# Review: Runnable Tool Gap

Date: 2026-05-19

This review focuses on the product gap between Longtask Harness as a protocol repo and Longtask Harness as a runnable CLI tool that a new user can install, initialize, run, inspect, and resume.

## Target First-Run Experience

```bash
npm install -g longtask-harness
lth init my-task --template coding
lth run my-task --worker codex-cli
lth status my-task
lth resume my-task
```

The strongest positioning is not "checkpoint-first protocol." It is a tool for running long AI coding tasks safely across rate limits, context resets, and multiple agents.

The README first screen should say:

```markdown
# Longtask Harness

Run long AI coding tasks safely across rate limits, context resets, and multiple agents.

Longtask Harness gives every task:
- a contract
- a checkpoint
- append-only run logs
- evidence before progress claims
- resumable worker handoff
```

## Current State

The repo is already more than a protocol sketch:

- `package.json` exposes global binaries: `lth` and `longtask-harness`.
- `lth init` creates task directories from templates.
- `lth run` executes bounded worker slices through local, Codex CLI, or Kimi adapters.
- `lth validate`, `lth verify`, `lth next`, `lth tick`, `lth record`, `lth evidence`, `lth classify`, `lth health`, `lth summary`, and `lth tail` already exist.
- `examples/resume-demo` proves a local recorded resume loop with run logs, evidence, checkpoint writes, and handoff evidence.

The missing piece is not the core architecture. The missing piece is the user-facing tool loop.

## Verified Gaps

| Priority | Gap | Verification | Recommended fix |
|---|---|---|---|
| P0 | README first screen still sells a protocol, not a runnable tool. | The opening line says "checkpoint-first protocol" and Quick Start uses `node src/cli.js`. | Replace the first screen with the tool positioning and global `lth` workflow. Move protocol detail below the quick start. |
| P0 | `lth status <task-dir>` does not exist. | The CLI has `summary` and `next`, but no status command matching the target workflow. | Add `status` as the friendly inspection command, backed by checkpoint, decision, last event, blocker, and evidence count. |
| P0 | `lth resume <task-dir>` does not exist. | Resuming currently requires users to understand `next`, checkpoint state, and `run`. | Add `resume` as a thin, explicit wrapper around the safe run decision and worker selection path. |
| P1 | The four-command demo path can fail for coding tasks without a configured repo cwd. | `codex-cli` requires `--cwd`, `task.codexWorker.cwd`, or `task.context.repoPath`. | Make coding `init` default to the current working directory, or make the README quick start explicitly pass `--cwd`. |
| P1 | The existing resume demo is useful but not emotionally concrete. | `examples/resume-demo` is a local recorded fixture, not a recognizable coding migration. | Add a React-to-TypeScript migration demo that shows killing the process midway and resuming from checkpoint. |
| P2 | Docs still split attention across protocol, adapters, and scheduler details before the core product loop. | README's first sections are Why, Core Files, and System Flow before install/run/status/resume. | Reorder docs so the first page proves the tool loop, then explains the protocol underneath it. |

## Recommended Implementation Order

1. Rewrite the README first screen around install, init, run, status, and resume.
2. Add `lth status <task-dir>` with human-friendly output and optional JSON later if needed.
3. Add `lth resume <task-dir>` as the explicit continuation command.
4. Adjust coding `init` so the target quick start has a valid Codex worker cwd.
5. Add smoke tests for `status`, `resume`, and the global-bin style command path.
6. Add `examples/react-typescript-migration-demo` with a concrete kill-and-resume story.

## Demo Direction

The demo should be framed as:

> Demo: Ask Codex to migrate a React app to TypeScript over multiple sessions. Kill the process midway. Resume from checkpoint.

Minimum credible demo contents:

- a small JavaScript React app fixture
- a task contract that asks for TypeScript migration
- checkpoint states for initial work, interrupted work, and resumed work
- append-only run logs showing the interruption and continuation
- evidence files showing build/test output before progress is claimed
- a demo README with exact commands using `lth init`, `lth run`, `lth status`, and `lth resume`

The demo does not need to be large. It needs to make the resume loop visible and believable.

## Product Assessment

Longtask Harness has a strong skeleton: task contract, checkpoint, run log, worker adapter, classifier, evidence, and verification. The next valuable move is presentation and command ergonomics. Users should understand in the first minute that this is something they can install and run, not only a protocol they can admire.
